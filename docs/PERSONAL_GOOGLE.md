# Google: foundation for personal connections

This module is dormant: it is not registered in `crm/web.py`, the migration is not applied, and no Google account has been contacted. Existing draft forms remain independent. It provides OAuth and bounded read-only Gmail and Calendar endpoints; it does not implement a connection-status UI or production rollout.

The intended registration seam is `app.router.add_routes(personal_google.routes(viewer, POOL))`, behind an explicit feature flag only after review. Apply migration 058 after 049. Configure `CRM_GOOGLE_CLIENT_ID`, `CRM_GOOGLE_CLIENT_SECRET`, `CRM_GOOGLE_REDIRECT_URI` (HTTPS, exact callback `/api/personal/google/callback`), plus the existing `ENCRYPTION_KEY`; store secrets outside the repository. Configure the exact redirect URI in Google Cloud. Middleware must allow the callback GET while requiring an authenticated same-user CRM session; maintain CSRF protection on start/disconnect POST/DELETE. Access logs and reverse proxy logs must omit callback query strings (authorization code and state). Do not enable until verified.

A saved Google draft binds kind, verified CRM identity, company, email and version. `POST /api/personal/google/{mail|calendar}/start` creates a 10-minute hashed one-time state and encrypted PKCE verifier; response URL is sensitive and must not be logged or cached. Callback consumes state before provider calls, rejects changed drafts, unexpected grants or account mismatch, and encrypts the refresh token. The single-use state and per-user/company advisory lock serialize start, callback and disconnect. Local disconnect removes credentials and invalidates pending states; best-effort Google revocation is reported separately because it can fail. A Google grant may span products: revocation can also affect other grants and must be tested before a UI is enabled.

The separate scopes are `gmail.readonly` and `calendar.readonly`, plus OpenID/email identity. Strict scope validation deliberately fails if Google returns additional grants; confirm actual provider behavior before launch. Google identity is obtained from the fixed HTTPS UserInfo endpoint using the returned access token, and must match the draft verified email. The helper `refresh_token` is internal, requires the same per-owner advisory lock, rejects changed drafts, persists rotated refresh tokens encrypted, and never returns the refresh token. No endpoint currently calls it.

Remaining release work: integration tests with an isolated PostgreSQL database covering callback replay, expiry, company/user mismatch, draft change, concurrent disconnect and refresh rotation; mock provider/network failures and revocation; verify callback log redaction, cookies, CSP and browser navigation; verify exact Google scopes and consent behavior; UI and status design; Google verification and operational key management. Do not log URLs, credentials, state, provider bodies, or raw exceptions. No external account or live server was tested.


Read-only APIs: `GET /api/personal/google/mail/search?q=...` returns at most ten messages with selected headers and snippet; no message bodies, attachments, or sending. `GET /api/personal/google/calendar/events?from=<RFC3339>&to=<RFC3339>` returns at most 100 primary-calendar events and `has_more`. `GET /api/personal/google/calendar/freebusy` accepts the same interval and queries only the primary calendar. Windows require explicit timezone and at most 31 days. All endpoints use the user's own scoped encrypted connection and return `Cache-Control: no-store`. Search query parameters may contain private data: suppress them in application and reverse proxy access logs. Google account scopes permit broader reads than these intentionally restricted endpoints; scope verification and app consent remain operational requirements.

The local tests use a disposable localhost PostgreSQL database named `google_test` with random private schemas and mocked Google responses; they refuse non-loopback and other database names. Callback success/replay/expiry, draft changes, user/company mismatch, identity mismatch, disconnect, refresh-token rotation and read endpoints were tested. They do not substitute for deployment middleware checks, concurrency stress, browser flows, Google verification or live API validation.

Google API references: https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list ; https://developers.google.com/workspace/calendar/api/v3/reference/events/list ; https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query .

## Gmail confirmed actions (dormant)

Migration 061 and `crm/personal_google_actions.py` implement an explicitly separate `gmail.send` consent and a prepare/confirm workflow. They are **not registered or enabled**. Register both `personal_google.routes(viewer, POOL)` and `personal_google_actions.routes(viewer, POOL)` behind a feature gate, after applying migrations 049, 058 and 061; all existing CRM authentication, CSRF, X-CRM and callback middleware remains mandatory. The action endpoints also require `X-CRM: 1`. Never rely on the header alone as authentication.

`POST /api/personal/google/mail/send-consent` creates a separately scoped, expiring, single-use, user/company/draft-bound PKCE state. The shared callback verifies Google account, scope and saved draft and stores a separate encrypted refresh token. `POST /api/personal/google/mail/send/prepare` accepts exactly `to`, `subject`, `body` and returns an immutable preview and hash; `POST /api/personal/google/mail/send/confirm` accepts exactly `id` and `payload_hash`. Both must be invoked only by the authenticated owner. Confirmation rechecks the actor immediately before an atomic durable claim and verifies current connection, account and grant versions. The Google send request is made at most once; `sending` after interruption and `unknown` must be treated as uncertain, never automatically retried. A successful response saves the provider ID. Disconnect clears pending states and read and write credentials locally, with remote revocation reported independently. Token refresh and all these routes use the same owner/company advisory lock.

Remaining requirements before enabling: independently review authentication, CSRF, session rechecks, SQL, concurrency and crash handling; add a confirmation UI with accessible full recipient/content preview; redact callback and mail-search query strings and request bodies in all logs; test real consent, actual granted scopes, token rotation/revocation behavior, OAuth app verification and provider errors in an isolated Google test account. Test process cancellation while holding a database lock. Provider outcomes can remain unknown and require human verification in Sent Mail. Both Gmail send and read permissions expose sensitive account capabilities; scope consent is separate from explicit confirmation of each message. Google may revoke related grants together. Calendar create, reschedule and cancel remain unimplemented.

Local tests use a separate localhost `google_test` PostgreSQL database and mocked Google calls; they cover consent, owner isolation, preview, confirmation, duplicate confirmation, disconnect, stale draft, refresh rotation and ambiguous outcome. No real Google account or email was used.
