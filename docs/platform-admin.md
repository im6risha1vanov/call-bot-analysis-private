# Админка платформы Averon

Бэкенд работает в процессе CRM. Контракт для интерфейса находится в `platform-admin.openapi.json`. Сервер возвращает признак `platform_admin` в `GET /api/me`. Административные маршруты начинаются с `/api/platform/admin`.

Откройте «Настройки → Админка платформы» под учётной записью Григория. Прямая ссылка начинается с `/#platform-admin`. Выберите компанию слева, затем нужный раздел в карточке компании. После публикации воронка и действие «Перевести сделку» появляются в обычном разделе «Сделки» у сотрудников с соответствующим доступом.

## Доступ и команды

- `CRM_PLATFORM_ADMIN_INVITE_ID` задаёт ID действующей директорской учётной записи Григория в домашней компании. Прямой вход обязателен. Тестовые сессии и переключение между аккаунтами не дают доступа к этому API.
- `CRM_PLATFORM_ADMIN_WRITES=1` разрешает изменение и запускает обработчик проверок интеграций. При значении `0` доступно чтение. Пустой ID закрывает раздел.
- Для изменений передавайте `X-CRM: 1` и уникальный `Idempotency-Key`. При повторе после сетевого сбоя используйте тот же ключ с тем же телом. Для следующих изменений начните с нового ключа. При конфликте версии перечитайте ресурс.
- Пароль, ключи Mango, код привязки Telegram и токен входящего вебхука передаются при записи. Для привязки Telegram создайте случайный код и откройте в нужном чате ссылку с параметром `start=aut_<код>` или `startgroup=aut_<код>` у бота CRM. Ссылку формирует клиент из известного имени бота и введённого кода.

## Настройка и проверка

1. Откройте компанию и прочтите `version` и `settings_sources`. В `PATCH /companies/{company_id}/settings` передайте текущую версию и изменяемые поля. `null` у параметра снимает значение компании. Для домашней компании при этом снова действует настроенное значение окружения, если оно есть. Лимит ИИ применяется в AveronGPT. Расход в рублях рассчитывается по существующей модели учёта CRM.
2. Права роли задаются как `denied` по разделам и операциям. Доступ по роли сначала ограничивают установленные модули и правила компании. Затем действующий API проверяет собственные ограничения роли и доступ к конкретной записи. Операции фонового конструктора правил учитывают настройку `automations.run` роли директора.
3. Получите текущую версию воронки. Сохраните черновик, откройте `preview` и опубликуйте с `remap` для занятых удаляемых этапов. Версия `0` содержит исходную воронку. У основной воронки сохраняются системные коды, связанные со звонками, презентациями и оплатой. При заданном списке переходов для этапа доступны перечисленные направления. Пустой список закрывает переход. Операция `POST /api/deals/{phone}/stage` проверяет предыдущий этап, версию целевой воронки и владельца сделки. Смена воронки доступна руководителю. Оплата отмечается через существующее действие в карточке.
4. В `GET /pipelines/{pipeline}/report?as_of=…` передайте время с часовым поясом. Исторический отчёт выбирает конфигурацию, опубликованную на указанную дату, и сохранённые к этой дате события. Для данных старой CRM, которые менялись на месте, например состояния открытых задач и карточки переписки, полный исторический снимок недоступен.
5. Создайте черновик правила с `version=0` или текущей версией существующего правила. Симуляция показывает совпавшие условия и отрисованные параметры действий на переданном примере. Публикация требует симуляцию этой версии и готовые подключения. Существующая опубликованная версия продолжает работать, пока редактор готовит черновик. Запуск записывает версию правила. Состояние `delivery_unknown` требует проверки в системе приёмника перед новой отправкой.
6. Для Mango и Google Sheets команда проверки возвращает `202` и ID операции. Поллинг `GET /operations/{operation_id}` показывает результат. Для Mango пустое тело проверяет сохранённые реквизиты, а новые реквизиты вступают в силу после успешной проверки баланса. При замене входящего вебхука передайте новый случайный токен и настройте отправителя на `/hook/<токен>`. В журнале хранится факт замены.
7. Для восстановления настройки используйте ID записи журнала и текущую версию. Для восстановления воронки или правила сохраните черновик с `restore_version` и опубликуйте его после проверки.

## Выпуск

1. Проверить, что код выпуска собран от текущей рабочей ревизии CRM. Выполнить миграцию `055_crm_platform_admin.sql` на тестовой PostgreSQL, затем выполнить тест `tests.test_platform_admin` и регрессию CRM.
2. Применить миграцию в среде выпуска. Она добавляет таблицы, фиксирует исходную версию воронки и сохраняет действующие настройки. Запустить сервис с подтверждённым ID Григория и режимом чтения. Через его прямую сессию сверить список компаний и карточки. Проверить, что другой директор получает `403`.
3. Включить запись после проверки. Для остановки изменений вернуть `CRM_PLATFORM_ADMIN_WRITES=0`. Для закрытия раздела убрать `CRM_PLATFORM_ADMIN_INVITE_ID`. Опубликованные воронки и правила продолжат работать в CRM. При необходимости отменить отдельную конфигурацию восстановлением версии или приостановить правило.

## Проверка в браузере

На отдельной базе с префиксом `callbot_methodology_test_` тест `tests.test_platform_admin` поднимает настоящий локальный сервер CRM. Задайте `METHODOLOGY_TEST_DATABASE_URL` и `CRM_ADMIN_PLAYWRIGHT` (путь к установленному модулю Playwright). При использовании системного Chrome задайте `CRM_ADMIN_CHROME` с путём к исполняемому файлу. Провайдеры Mango и SMTP заменяются тестовыми обработчиками. Переменная `CRM_ADMIN_SCREENSHOTS` позволяет сохранить снимки рабочего и мобильного экранов в указанную папку.
