# Командные поручения и встречи: backend

Код подготовлен для отдельного развёртывания; миграции и обработчики не запускают звонки и не переносят личные задачи. Применить миграции 056 и 057 последовательно с остальными миграциями CRM; `scripts/crm_setup.sh` включает их. Перед включением настроить `CRM_PERSONAL_PILOT_TELEGRAM_IDS` как список Telegram ID пилота через запятую; по умолчанию переменная не задана и доступ закрыт; отдельное включение для того же пилота не требуется. Нужны действующий персональный CRM invite и активный сотрудник той же компании. Тестовые и support-сессии запрещены. Проверять фактические настройки и БД в целевой среде; локальные тесты не подтверждают production.

## Поручения

HTTP использует действующую CRM-сессию, а изменения также требуют `X-CRM: 1` и непустой `Idempotency-Key` до 128 символов. Значения примеров вымышленные. `description` — ожидаемый результат. `assignee_id` — Telegram ID активного сотрудника из пилота; он отличается от постановщика. `due_at` — ISO 8601 с часовым поясом. Необязательный `deal_id` — 10 цифр номера сделки: существующая CRM проверяет её доступность обоим участникам. Личные проекты не используются в командных поручениях.

```http
POST /api/team/assignments
X-CRM: 1
Idempotency-Key: example-create-1
Content-Type: application/json

{"title":"Подготовить предложение","description":"Согласованный вариант для клиента","assignee_id":102,"due_at":"2027-01-15T12:00:00+03:00","deal_id":"9991234567"}
```

`deal_id` и `due_at` можно опустить. Ответ `201` содержит `assignment` с `id`, `version` и `status`. Доступные списки: `GET /api/team/assignments?filter=assigned`, `?filter=created`, `?filter=to_review`. `GET /api/team/assignments/{id}` и `.../{id}/history` доступны только постановщику и исполнителю в своей компании. `GET /api/team/mine` объединяет командные поручения исполнителя и только его собственные личные задачи; поле `kind` различает `team` и `personal`.

```http
PATCH /api/team/assignments/123
X-CRM: 1
Idempotency-Key: example-edit-1
Content-Type: application/json

{"version":1,"description":"Уточнённый ожидаемый результат"}
```

Редактирует постановщик до передачи на проверку. Каждое изменение требует текущую версию и отдельный ключ: устаревшая версия вернёт `409`. Повтор того же запроса с тем же ключом вернёт сохранённый результат без повторного изменения; использование ключа с другими данными вернёт `409`. Следующее действие использует новую версию и новый ключ.

```http
POST /api/team/assignments/123/submit
X-CRM: 1
Idempotency-Key: example-submit-1
Content-Type: application/json

{"version":2,"result_text":"Подготовил проект предложения","result_links":["https://example.org/proposal"]}
```

Исполнитель может `start`, `block` с обязательным `blocker`, `clear_blocker`, `submit` с обязательным текстом результата и необязательным массивом HTTP(S)-ссылок. Препятствие хранится отдельно и не меняет статус; при сдаче результата оно очищается. Комментарий возврата хранится отдельно в `review_note` и в истории. Постановщик может `return` с обязательным непустым `comment`, `accept`, `cancel`. Для действий без текста тело содержит только `version`. Принятие и возврат возможны только после `submit`. Каждый переход сохраняет снимок в истории.

Внутреннее создание из встречи вызывает `team_assignments.create(conn, (company_id, telegram_user_id), data, source_meeting_id=..., source_item_id=..., idempotency_key=...)` внутри общей транзакции; функция не открывает собственную транзакцию. Сторона вызова проверяет доступ к встрече и идентичность пользователя. `team_assignments.identity(db, viewer)` проверяет право входа, а `transition` содержит правила переходов.

## Проверки

Для изолированной тестовой базы PostgreSQL задать `TEAM_TEST_DSN` и запустить `python -m unittest tests.test_team_assignments -v`. Тест удаляет и пересоздаёт схему `public`, поэтому DSN должен указывать только на выделенную тестовую базу. Проверяются конкурентные повторы и версии, изоляция компаний и личных задач, переходы проверки и сохранение статуса при препятствии. Эти проверки не заменяют приёмку в целевой среде.

## Встречи

Импорт доступен только локальному адаптеру через `POST /api/internal/team/meetings/import`: `Authorization: Bearer <CRM_MEETINGS_IMPORT_TOKEN>`, `X-CRM: 1`, локальный Host `127.0.0.1:8095`, без forwarded-заголовков. Токен должен содержать не менее 32 символов и храниться в окружении сервера. Разрешённые источники задаются в `CRM_MEETINGS_SOURCES_JSON`, например с вымышленными значениями: `{"teams_auto":{"company_id":1,"series_id":"weekly","owner_ids":[101]}}`. Проверить конфигурацию перед включением адаптера; не помещать действующий токен в репозиторий.

Участникам-владельцам встречи доступны `GET /api/team/meetings`, `GET /api/team/meetings/{id}`, `GET /api/team/meetings/{id}/snippets?ids=u-...` и `GET /api/team/meetings/agenda?series_id=weekly`. Повестка показывает поручения только их постановщику или исполнителю. `PATCH /api/team/meetings/{id}/protocol` принимает `{"version":1,"protocol":{...}}`, а `POST /api/team/meetings/{id}/convert` — `{"item_id":1,"assignee_id":102}` с необязательными `title`, `description`, `due_at`. Повторное преобразование того же пункта не создаёт второе поручение. Признаки сокращения исходного материала указаны в `state.capture_warning` и `transcript.export_truncated`.

Связь со сделкой перепроверяется для каждого текущего участника при чтении, включая историю и повторный ответ: если доступ утрачен, `deal_id` возвращается как `null`, а само поручение остаётся доступным. При повторе изменения дополнительно проверяются действующий сотрудник и текущее участие в поручении.
