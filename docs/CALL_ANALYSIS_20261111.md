# Разбор звонков колл-центра

Реализация в ветке `feat/harness-crm` (рабочая папка `averon-harness-crm`).
Код: `crm/call_analysis.py`, схема `crm/call_analysis_schema.py`, Deepgram-клиент
CRM `crm/deepgram.py`, экран `crm/static/callanalysis.js`.

## Что сохранилось

Экран «Колл-центр» и его счёт для Ольги не переписаны: клиенты, номера,
первичные/повторные звонки, «Заинтересованный», сумма по тарифам и выгрузка
CSV по-прежнему считаются `crm/cabinet.py` и `crm/callcenter_db.py`. Новый
разбор — отдельный экран по кнопке «Разобрать звонки».

## Операторы и источники

| Оператор | Добавочный | Источник звонков | Как подтверждён |
|---|---|---|---|
| Ольга | `CALL_ANALYSIS_OLGA_EXT`, единственный `KITCHEN_EXTENSIONS` или единственная активная «Ольга» в `employees` | `calls` (Mango) | код сам по себе добавочный не подтверждает |
| Оксана Кирнева | 15 | `calls` (Mango) | подтверждено владельцем |
| Робот | 13 | `calls` (Mango); `robot_calls` — только расшифровка/сценарий по совпадению телефона и времени; если журнала Mango нет, его собственный журнал с явной пометкой | `crm/accounts.py`, `crm/lead_qualification.py` |

`CALL_ANALYSIS_OPERATORS` может заменить сопоставление: JSON
`{"olga":{"extension":"14"}}` или строка `olga=14,oksana=15,robot=13`.
Если добавочный Ольги не подтверждён, экран показывает пустое состояние и
просит настройку, а не подставляет 14 наугад.

Другие настройки: `CALL_ANALYSIS_OLGA_EXT` — отдельный добавочный Ольги;
`CALL_ANALYSIS_SCRIPT` — id скрипта операторов (по умолчанию `hh_ru`);
`CALL_ANALYSIS_ROBOT_SCRIPT` — id сценария робота для проверки совместимости;
`CALL_ANALYSIS_WORKER=off` — выключить фоновый цикл (по умолчанию включён).

## Период и запуск

* Даты вводятся как календарные дни и трактуются по Москве; конец включается,
  в запрос к базе уходит исключающий конец следующего дня.
* Максимум 31 день за прогон.
* Кнопка запуска создаёт прогон в `call_analysis_runs`, пункты — в
  `call_analysis_items`.
* Повторный запуск за те же компанию, оператора, добавочный и даты возвращает
  существующий прогон (`UNIQUE(client_id, dedup_key)`); повторных пунктов нет
  (`UNIQUE(run_id, call_ref)`).
* HTTP-запрос только ставит задачу. Расшифровка Mango/Deepgram и разбор идут в
  фоновом цикле `call_analysis.loop`, который запускается из `crm/web.py`.
  После перезапуска CRM незавершённые прогоны возвращаются в очередь и
  продолжаются по непобработанным пунктам.

## Этапы

1. попытка;
2. ответ живого человека;
3. содержательная квалификация по найму;
4. подтверждена потребность в найме;
5. подтверждены оба критерия hh.ru: нет регистрации и нет кабинета
   работодателя;
6. согласие на звонок специалиста;
7. фактический лид в CRM.

Этапы 2–6 определяются по расшифровке консервативно. Если говорящих не удалось
разделить, расшифровка пустая/неуверенная, запись недоступна или сценарий не
совпадает со скриптом hh.ru, этап помечается `unknown`/`not_applicable`, а не
«провалом оператора». Причина обрыва имеет группу: качество базы, технический
обрыв, возможный пропуск оператора, клиент, CRM или неизвестно.

Для робота проверяется сценарий из `robot_calls.operator`. Сейчас в репозитории
есть сценарий `kitchen` (кухни), а не hh.ru, поэтому критерии hh.ru для таких
звонков помечаются «не применимо», а не нарушением скрипта hh.ru.

## Лиды CRM и неизвестная атрибуция

Лидом считается только человеческая отметка в CRM:

* `crm_leads.status` — `interested`, `proposal` или `meeting`;
* `crm_outcomes.outcome` — `interested`, `proposal` или `meeting`;
* `cc_leads.attempts` — результат «Заинтересованный».

Запись кампании робота, `robot_calls.outcome='interested'`, `lead_attempts` и
предположение модели лидом не считаются. Если номер не связан ни с одной
CRM-записью, он попадает в «неизвестную атрибуцию». Google Таблицы в этом
модуле не читаются: номера и кампании из них не смешиваются с журналом Mango.
Сверка с CRM показывается только когда в CRM есть отмеченные лиды; иначе явно
написано, что сравнение недоступно.

## Права, компания и Telegram

* Запуск, сохранение и отправка — только `Viewer.role == 'director'` и
  `Actor.role` из `owner`/`head`; тестовый и support-входы запрещены.
* Компания и автор берутся из серверной сессии и `crm_invites`/`employees`, не
  из тела запроса.
* Telegram-адресат — только `employees.telegram_user_id` владельца учётной
  записи, запустившей разбор, при активной записи `owner/head` в той же
  компании. `chat_id` из браузера, компании, общей группы или другой учётки не
  принимается.
* Если действующей личной привязки нет, `can_telegram=false`, кнопка не
  показывается, а прямой POST отклоняется.
* Сводка Telegram содержит только числа: период, звонки, этапы, покрытие,
  сверку. Телефонов, контактов и полных расшифровок в ней нет.
* Сохранение (`saved_at`) и повторное открытие разбора доступны в CRM; отправка
  в Telegram — отдельное явное действие.

## Проверки

```powershell
python -m py_compile crm/call_analysis.py crm/call_analysis_schema.py crm/deepgram.py crm/web.py crm/tour.py
node --check crm/static/callanalysis.js
node --check crm/static/callcenter.js
python -m unittest tests.test_call_analysis -v
```

Тесты покрывают: сопоставление операторов без догадки, московские границы,
ключ дедупликации, полную/частичную/пустую/неуверенную расшифровку,
автоответчик, несовместимый сценарий робота, человеческие лиды CRM,
неизвестную атрибуцию, отсутствие сравнения, отсутствие контактов в Telegram,
роли и уникальность аддитивной схемы.

## Ограничения и что нужно на сервере

* Штатная выкладка CRM переносит только `crm/`, `tests/` и `docs/` и не
  запускает SQL-миграции. Поэтому `crm/call_analysis_schema.py` при первом
  обращении аддитивно создаёт только недостающие таблицы и индексы. Если у
  пользователя БД нет права `CREATE`, раздел вернёт ошибку, а остальная CRM
  продолжит работать; тогда нужна отдельная стандартная миграция с теми же
  `CREATE TABLE IF NOT EXISTS`.
* Код не выкладывался, реальные Mango/Deepgram/Telegram не вызывались, звонки
  не совершались.
* Добавочный Ольги на сервере нужно подтвердить настройкой, если его нет в
  единственном `KITCHEN_EXTENSIONS` или в сотрудниках.
* Для робота по-прежнему используется существующий сценарий. Если появится
  сценарий hh.ru, его id нужно указать в `CALL_ANALYSIS_ROBOT_SCRIPT`.
