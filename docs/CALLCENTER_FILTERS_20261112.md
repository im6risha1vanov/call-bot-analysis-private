# Фильтры периода и сотрудников в «Колл-центре»

Ветка `feat/callcenter-filters-live`, база — серверный коммит
`60f177de17d2277a3af02ec1550b812be49de2a4`. Код: `crm/cabinet.py`,
`crm/callcenter_db.py`, `crm/callcenter_access.py`, `crm/web.py`,
`crm/static/callcenter.js`. Тесты: `tests/test_callcenter_filters.py`.

## Что добавилось

В шапке «Колл-центра» появились два переключателя — как в «Сводке»
(Сегодня / 7 дней / 30 дней / Месяц и «Весь отдел» / сотрудник). По умолчанию
выбрано «Всё время» + «Весь отдел»: страница открывается с теми же числами, что
и раньше.

Фильтры меняют всю страницу: цифры, график по дням, таблицу клиентов, суммы,
перезвоны, базы и источники. Ничего не переписано заново: те же `parse_client` /
`DbSource.summary`, разбор строк вынесен в записи лидов (`sheet_records`,
`parse_records`).

Ранее сделанный разбор звонков (`crm/call_analysis.py`, экран «Разобрать
звонки») не менялся.

## Что означают фильтры

* **Период** — календарные дни по часовому поясу компании, включительно.
  Попытка попадает в срез по своей дате звонка (`Дата звонка 1…3` в листе,
  `cc_leads.attempts[].d` в базе). Попытки без даты в период не попадают, их
  число отдаётся в `filters.undated` и показывается подсказкой.
* **Сотрудник** — автор попытки. В базе это добавочный Mango из
  `cc_leads.attempts[].by`, в таблице — колонка «Оператор» (см. ниже).
  Сотрудники берутся из того же сопоставления, что в разборе звонков
  (`call_analysis.operator_specs`): Ольга, Оксана (доб. 15), робот (доб. 13).
  «Весь отдел» — все попытки, включая те, где автор не записан; их число
  отдаётся в `filters.unattributed`.
* **Сумма** — цена каждой попытки по тарифам: «Заинтересованный» по своему
  тарифу, первая попытка по тарифу первичного звонка, остальные — повторного.
  Поэтому срез по сотруднику или периоду складывается из звонков, а не из
  «Суммы» лида.

## Два источника данных

| Что нужно фильтру | Google-таблица «Прозвон лидов» | Колл-центр в базе |
|---|---|---|
| Период (даты звонков) | есть: «Дата звонка 1…3» | есть: `attempts[].d` |
| Автор звонка | **нет**: в листе нет колонки оператора | есть: `attempts[].by` (добавочный Mango) |
| Сумма за период | **нет**: «Сумма» посчитана по лиду целиком и по звонкам не делится | есть: цены компании по каждой попытке |

Отсюда поведение:

* В таблице фильтр по сотрудникам не показывается, а сервер отвечает на такой
  запрос понятной ошибкой (`filters.operator_available = false`,
  `operator_reason`). Это не «нет данных за период», а «источник не хранит
  автора звонка».
* В таблице сумма за период не считается: KPI и колонка «Сумма» показывают
  прочерк с пояснением (`sum_available = false`, `sum_reason`). Подставлять
  пересчёт по тарифам вместо суммы листа нельзя: формула листа и тарифы могут
  расходиться, а выдуманные показатели недопустимы.
* Если владелец добавит в лист колонку «Оператор» (варианты названия:
  «Оператор», «Сотрудник», «Менеджер», «Оператор звонка», «Кто звонил»), разрез
  по сотрудникам в таблице заработает без правок кода: чтение листа расширено
  до `A:Z6000`. Сумма за период в таблице всё равно останется недоступной.
* Робот: его звонки пишутся в свой журнал (`robot_calls`) и в попытки
  колл-центра не попадают. Поэтому в базе срез «Робот» будет пустым, пока его
  попытки не записываются с добавочным 13; это видно по `filters.operators[].
  attempts = 0`, а не маскируется нулями без пояснения.

## Доступ: Григорий, Евгений, pivondopola

Проверка серверная (`crm/callcenter_access.py`), её вызывает `/api/callcenter`
при наличии `period` или `operator`. Без фильтров раздел работает как раньше
для всех, кому он был доступен: сохранена текущая функциональность.

Кому выдаётся доступ:

1. Вход — действующий директор из личной сессии: `Viewer.role == 'director'`,
   `Actor.role` — `owner` или `head`, не тестовый и не служебный вход.
2. Запись сотрудника находится среди активных `employees` компании (роль
   `owner`/`head`) и совпадает с одним из трёх:
   * **Григорий** — слово «Григорий» в ФИО или добавочный `head:<транслит>`;
   * **Евгений** — то же с «Евгений»;
   * **pivondopola** — точный `employees.telegram_username = 'pivondopola'`.

Если подходящих записей нет или их несколько, доступ не выдаётся и в ответе
видно, какое сопоставление не подтверждено (`targets[].reason`). Догадок нет:
«Гриша» не равно «Григорий», две записи «Григорий» — отказ.

Явный список владельца `CALLCENTER_FILTER_VIEWERS` (добавочные, Telegram ID или
ники через запятую) подтверждает доступ, если имя в базе записано иначе.

## Что не подтверждено в этой рабочей папке

Точные CRM-идентификаторы Григория, Евгения и pivondopola **не подтверждены**:
в репозитории нет ни дампа базы, ни выгрузки `employees`, а доступ к серверу
(SSH/БД) не используется. Поэтому сопоставление выполняется на сервере при
первом запросе по правилам выше, а не зашито в код.

Проверить на сервере (только чтение, без изменения данных):

```sql
SELECT extension, role, full_name, telegram_user_id, telegram_username
FROM employees
WHERE client_id = <ID компании> AND archived_at IS NULL AND role IN ('owner','head')
ORDER BY extension;
```

Ожидаемо: одна активная запись владельца/руководителя с «Григорий», одна с
«Евгений», одна с ником `pivondopola`. Если ник пуст или записей несколько —
либо заполните `telegram_username`, либо задайте `CALLCENTER_FILTER_VIEWERS`.

## Проверки

```powershell
python -m py_compile crm/cabinet.py crm/callcenter_db.py crm/callcenter_access.py crm/web.py
node --check crm/static/callcenter.js
python -m unittest tests.test_callcenter_filters -v
python -m unittest tests.test_crm.PureTests tests.test_crm.CallcenterTests tests.test_call_analysis
```

`tests/test_callcenter_filters.py` покрывает: границы периода, срез по датам,
чтение колонки «Оператор», недоступность разреза и суммы в таблице, срез по
сотруднику и цены в базе, неизвестного сотрудника, доступ трёх пользователей,
отказ другому директору, тестовому и служебному входу, отказ при неоднозначном
имени и при отсутствии ника, подтверждение списком `CALLCENTER_FILTER_VIEWERS`.

Полный прогон `python -m unittest discover -s tests -t .` в этой папке: 791 тест,
из них 287 пропущены (нужна тестовая PostgreSQL: `METHODOLOGY_TEST_DATABASE_URL`).
Набор падающих тестов совпадает с прогоном до изменений (3 падения и 112 ошибок
окружения: нет базы, ограничения временной папки, переводы строк), новых
падений нет.

## Миграции и зависимости

* Миграций нет: новых таблиц и колонок не добавляется. Используются
  существующие `employees` (`full_name`, `role`, `telegram_user_id`,
  `telegram_username` из `019_crm_staff.sql`, `archived_at` из
  `041_crm_staff_activity.sql`) и `cc_leads.attempts[].by` (был в
  `033_callcenter.sql`).
* Новых зависимостей нет. Необязательная настройка: `CALLCENTER_FILTER_VIEWERS`.
  Добавочные Ольги/Оксаны/робота берутся из прежних `CALL_ANALYSIS_*`,
  `KITCHEN_EXTENSIONS` и справочника сотрудников.

## Ограничения

* Разрез по сотрудникам для Google-таблицы появится только с колонкой
  «Оператор»; до этого он честно недоступен.
* Сумма за период в Google-таблице не считается.
* Звонки робота в попытках колл-центра не записываются: в разрезе «Робот» будет
  пусто, пока они не начнут писаться с добавочным 13.
* Код не выкладывался, SSH и серверная база не использовались, звонки и
  сообщения не отправлялись.
