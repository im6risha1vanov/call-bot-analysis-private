# Импорт встреч рекордера в CRM

Отдельный процесс читает только завершённые встречи автоматического наблюдателя Teams, начиная с заданного момента, и передаёт снимок в CRM через 127.0.0.1. Он не меняет рекордер, анализ или отправку в Telegram. Это подготовленные файлы; установка и запуск здесь не производились.

Источник допускается только при совпадении ID встречи с записью `started` в `teams/dispatch-ledger.json`, ID Teams-события в `status.json` и файла события с закреплённым ID чата «ОП Аверон». Ручные встречи, самопроверки, старые встречи и незавершённые состояния исключаются. systemd передаёт журнал через LoadCredential как приватный снимок при каждом запуске; права исходного root-only файла не меняются.

Передаётся весь исходный transcript.json с добавленными стабильными ID реплик (хеш источника, времени, говорящего и текста). ID заметки report.json преобразуются из номеров строк в эти ID. Отчёт импортируется только при наличии соответствующего кеша анализа и если он не старше расшифровки; ошибочный анализ передаётся с флагом analysis_error. При изменении расшифровки старый отчёт удаляется из снимка и повторно не приписывается новым словам. Если отчет готов позже, снимок обновится на следующем проходе. Статусы partial/failed сохраняются.

Лимит запроса 390 000 байт. Если расшифровка больше, первыми сохраняются все реплики, на которые ссылается отчёт, и затем другие реплики в исходном порядке; экспорт явно маркируется как сокращённый. Если даже это не помещается, отправляется только статус с предупреждением. Оригиналы остаются у рекордера. CRM должна показывать capture_warning. Изменение исходника вызовет повторную отправку. Учёт завершённых снимков хранится в `crm-import/imported.json`, обновляется атомарно только после успешного ответа CRM. Неоднозначный ответ вызовет идемпотентный повтор той же ревизии. Отправка ограничена тремя попытками за проход; следующий проход по таймеру повторяет ошибки.

## Подготовка администратором сервера

1. Сверить живые версии `recorder.py`, `teams_supervisor.py`, `meeting_reports.py` и формат исходных файлов с локальной копией, на которой построен адаптер; подтвердить адрес CRM `127.0.0.1:8095`. Проверить, что сервису `averon-meetings` доступны чтение `sessions`, соответствующих `teams/events`, `notifications/<id>/report.json` и каталогов `analysis-*`. Доступ к журналу обеспечивает systemd LoadCredential; секреты записи Teams сервису импорта не нужны.
2. Скопировать `importer.py` в `/opt/averon-meetings-crm-import/importer.py`; создать каталог `/var/lib/averon-meetings/crm-import`, владелец `averon-meetings:averon-meetings`, режим 0700. Установить два unit-файла из этой папки в `/etc/systemd/system/`.
3. Создать `/etc/averon-meeting-crm-import.env`, владелец root, режим 0600, и записать туда значения (без кавычек и пробелов в токене):

```
CRM_MEETINGS_IMPORT_URL=http://127.0.0.1:8095/api/internal/team/meetings/import
CRM_MEETINGS_IMPORT_TOKEN=<секретный токен импорта CRM>
MEETINGS_IMPORT_NOT_BEFORE=2026-11-19T00:00:00Z
```

Дату заменить фактическим согласованным моментом включения; время обязательно с часовым поясом. Токен должен совпадать с `CRM_MEETINGS_IMPORT_TOKEN` в CRM; не хранить его в Git и не показывать в журнале. CRM также требует настроить `CRM_MEETINGS_SOURCES_JSON` с компанией, серией и владельцами `teams_auto`.
4. Проверить синтаксис `python3 -m unittest -v test_importer` в копии исходников. До включения таймера проверить права чтения от имени пользователя сервиса без вывода содержимого встреч: для выбранных путей, кроме root-only журнала; проверить LoadCredential через запуск тестовой службы без вывода содержимого. Выполнить `systemctl daemon-reload`, затем по согласованию включить `systemctl enable --now averon-meeting-crm-import.timer`. Проверить `systemctl list-timers averon-meeting-crm-import.timer` и `journalctl -u averon-meeting-crm-import.service`; запись `imported <id>` означает успешный ответ API, после чего отдельно проверить карточку и права доступа в CRM. Остановить только импорт: `systemctl disable --now averon-meeting-crm-import.timer`.

## Изолированная проверка

Локальные unit-тесты создают временные фиктивные файлы и не обращаются к сети или рабочей CRM. Для сквозной проверки подготовить отдельную тестовую базу CRM и изолированную копию структуры рекордера; не размещать фиктивные встречи в рабочем `sessions`. У импортёра корень фиксирован в `BASE`, поэтому в тестовом процессе переопределить `importer.BASE` на временный каталог и направить запрос в отдельный тестовый loopback CRM на том же контракте. Тест должен подтвердить повторную доставку, поздний отчёт, обновление текста и права доступа; эти проверки не подтверждаются одним запуском unit-тестов.
